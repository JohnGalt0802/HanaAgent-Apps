# hana-downloader v2 App 七象限投递能力测试报告

- 测试日期：2026-09-10
- 宿主版本：HanaAgent 0.946.2（win32-x64）
- 被测对象：`hana-downloader` v2 App（v0.16.0），下载引擎为 local-machine 受管程序
- 测试驱动：`download-file` / `download-command` / `download-wait` / `download-cancel`
- 结论：**6/7 通过**；象限 5/6 属 v2 架构差异，非缺陷（见文末）

---

## 一、坐标系

沿用插件时代沉淀的二维模型：

- **维度 A · 投递时机**：对话**未收束**（unsettled，模型还在跑）/ 已**收束**（settled，模型已停）
- **维度 B · 终态类型**：完成（done）/ 取消（canceled）/ 卡滞（stall）

3 × 2 = 6 个象限，另加象限 7（卡滞 → 恢复 → 完成）。

**v2 与 v1 的关键差异**：v1 用 steer（同步注入）/ deferred（异步投递）两条通道，且区分
suppress 策略；v2 统一交给宿主 `ctx.tasks`，语义只有一条——`delivery: "next-step"`
（不打断在途请求，下一次输入收集点接收；空闲会话则启动后续回合）。
所以 v1 那套「是否 suppress」的判定在 v2 里不再适用，测试预期相应简化。

## 四、象限 5/6 为何不适用

卡滞（stall）是**中途状态**，不是终态；而 v2 的任务模型有一条硬约束：

`ctx.tasks.create` 若要投递到会话（`delivery: "next-step"`），**必须携带当前有效的
callToken**；没有令牌时 `create` 只能建 `scope:"app"` 且 `delivery` 必为 `"none"` 的任务，
投不到任何会话。而 callToken **只在工具 `execute` 期间有效**，下载中途早已过期。

实测报错：

```
stall notice ERR | v2 app "hana-downloader" needs a current valid callToken that names a session
```

所以 v2 的投递模型天然是「**一次 execute → 一条终态通知**」。中途的 stall 只能：
1. 记录在引擎侧（本项目已在 `app-data/hana-downloader/stalled/` 落盘，供前端卡片展示）；
2. 或由前端卡片轮询展示，不惊动模型。

这不是实现缺陷，是架构边界。若将来需要「中途惊动模型」，需要宿主提供不依赖
callToken 的会话投递入口（或提供长时间有效的投递票据）。

**对模型的实际影响**：模型不会在下载卡滞时被打断，只会在最终终态（含 `interrupted`）
收到一次通知。卡滞期间用户仍可从卡片看到状态并决定取消。

## 五、附带发现

1. **引擎进程曾意外退出一次**（象限 4 首轮）：`engine fetch /download failed: fetch failed`，
   4317 端口无监听。宿主日志中**无任何退出痕迹**（静默消失），且宿主不会自动重启受管进程。
   **已修**：app 侧新增 30 秒存活探活，不可达则重拉并等就绪。实测杀掉引擎后 1 秒内自愈。
2. **取消终态已对接 `ctx.tasks.cancel`**（原走 `fail`）。app 侧日志确认 `tasks.cancel OK -> canceled`。
   但宿主回执仍是 `status="failed"`（正文为 "canceled"）——这是宿主侧的映射行为，
   已在本报告记录，待与宿主侧确认是否预期。
3. **命令型同步验证过**：`download-command`（git-clone）在无网络环境下正确返回
   「命令退出码 128 + stderr 尾部」，失败路径投递正常。
4. **无凭据 / 带票据的转发路由对比**：`/routes/engine/*` 无凭据时 403 `missing_credential`，
   带 owner 登录态或 `X-Hana-App-Surface-Session` 时 200，与宿主鉴权文档一致。
