# 宿主缺陷：v2 应用工具的流内卡片（`details.card`）不渲染

- 宿主版本：HanaAgent **0.970.9**（win32-x64）
- 复现应用：`hana-downloader` v0.90.3（v2 App，`invocationStyle: "sdk_tool"`）
- 定位日期：2026-09-13
- 定位方式：读 bundle 源码 + 在宿主 bundle 内临时插诊断日志（已还原）

## 一句话

**宿主在投影 v2 应用工具的结果时，丢了工具的真实名字**，于是卡片归属解析失败，卡片被静默丢弃。

## 现象

1. 应用工具返回的 `details.card` 是完整的（`pluginId` / `route` / `title` / `cardForm` / `preferredWidthPx` 都在，会话 jsonl 里有原文）。
2. 聊天流里**不出现**卡片。
3. `/api/sessions/messages` 返回的顶层 `blocks` 里 **一条 `plugin_card` 都没有**。
4. 宿主日志里**没有** `dropping plugin card: claimed pluginId ... !== tool owner ...` 警告 —— 说明归属是"没查出来"，而不是"查出来但不匹配"。

## 投影链路（0.970.9 bundle，行号为该文件内位置）

```
工具结果 → hV(toolName, details, ...)                       (~53564)
        ├─ resolveAppMessageRenderer(customType) 命中 → 直接产卡并带 channel:"app"（~53581，**这条路正常**）
        └─ 未命中 → resolveToolOwner(toolName) → voe(pluginRuntimeV2, toolName)  (~53601)
                      └─ owner=null → Z_t() 产卡但**不带** channel:"app"（~53465）
                                        └─ 被 Qoe() 过滤：无 channel 的卡要求 pluginManager.getPlugin(id)，
                                           v2 应用不在 v1 插件表 → **静默丢弃**（~53611）
```

`voe()`（~53498）要求"恰好一个已加载的应用拥有该工具名"：

```js
function voe(t, e) {
  if (!t || typeof t.list != "function" || typeof t.toolBelongsToPlugin != "function" || ...) return null;
  const s = [];
  for (const i of t.list())
    i?.state === "loaded" && t.toolBelongsToPlugin(i.id, e) && s.push(i.id);
  return s.length === 1 ? s[0] : null;
}
```

## 运行时诊断结果（关键证据）

在 `voe()` 内插日志，重启后触发若干工具调用，统计 66 条记录里被查询的"工具名"：

```
exec_command: 29    loop_control: 9    tool_call: 6
write: 6     read: 5    write_stdin: 4    edit: 3    web_search: 2    grep: 1    ls: 1
download-*: 0        ← 一次都没有
```

单条样例（名册本身是好的，问题在查询键）：

```
[DIAG-voe] tool="exec_command" apps=[
  jimeng-cli(loaded,owns=false,names=[]),
  [token](failed,owns=false,names=[]),
  hana-downloader(loaded,owns=false,names=[download-file|download-wait|download-cancel|download-command]),
  powershell-tool(loaded,owns=false,names=[powershell|powershell_task|powershell_cancel]),
  savetoken(failed,owns=false,names=[])
] matched=[]
```

**结论：**
- 工具名册（`toolNamesByPlugin`）**内容正确**，`download-file` 在册。
- 但投影时查询键是 **`tool_call`**（泛化名），不是 `download-file` → `owns` 全 false → `matched=[]` → owner=null → 卡片无 `channel` → 被丢。
- 宿主内置工具（`exec_command`/`read`/`write`…）用的是**真实名**，能正常进入投影（它们不归任何应用所有，`owns=false` 属正常）。
- v2 应用工具那 6 次 `tool_call` 就是它的"残影"。

## 根因（一行）

`J_t()`（~53560）：

```js
function J_t(t, e) {
  if (t !== WA) return t;                 // WA === "tool_call"
  const s = e?.bridgedTool?.name;         // ← 真实名只从这里取
  return typeof s != "string" || !s || s === WA ? t : s;
}
```

`details.bridgedTool` 由 `cte()`（~172427）注入，值是 `{ name, server: ownerId }`（`e` 是 MCP/连接器侧的 owner）。**这是给 MCP / 连接器工具用的通道**；SDK 桥接的 v2 应用工具结果里没有这个字段，于是 `J_t` 原样返回 `"tool_call"`。

## 对照实验（排除法）

| 通道 | 结果 |
|---|---|
| `details.card`（本缺陷涉及的路） | ✗ 卡片进不了 `blocks`（`plugin_card` 计数 0） |
| `session:send-custom` + `contributes.messageRenderers`（走 `resolveAppMessageRenderer`） | ✓ 卡片正常产出，带 `channel:"app"`，状态 `mounted/ready`，聊天流可见 |

两者只差"是否需要归属解析"，所以断点就在归属解析这一环。

## 建议修法（任一即可）

1. **给 SDK 桥接工具也填 `bridgedTool`**（或等价字段），让 `J_t` 能取到真实工具名 —— 最贴近现有设计。
2. `voe()` 返回 null 时，允许 `Z_t()` 采用 `details.card.pluginId` 作为归属（该字段应用已经填了，且可校验"该 id 是已加载的 app"）。
3. `Qoe()` 对"无 `channel` 但 `pluginId` 属于已加载 v2 app"的卡片放行。

## 复现 / 验证方式

1. 安装任一 v2 App，其工具返回 `details: { card: { pluginId, route, title, cardForm } }`。
2. 调用该工具。
3. 查 `/api/sessions/messages?path=<session>`：期望 `blocks` 中出现 `plugin_card`（带 `channel:"app"`）；当前实际为 0 条。

## 2026-09-13 下午修正：上面的「建议修法 1」不成立

上面推测“补上 `bridgedTool` 就能让 `J_t()` 取到真实工具名、从而恢复归属解析”——
**这个是错的**。把 `hV()` 整个读完可以看到，`J_t()` 修出来的真名**只用于查内置渲染器表**：

```js
function hV(t, e, s, i, r) {
  const a = Poe[J_t(t, e)];                   // 只有这里用了修正后的名字
  if (a) { … }
  const c = r?.resolveAppMessageRenderer(t);   // ← 用的是原始 t
  if (c) { 产卡 } else {
    const d = r?.resolveToolOwner(t);          // ← 也是原始 t
  }
}
```

归属解析（`resolveAppMessageRenderer` / `resolveToolOwner`）拿到的仍是**原始工具名**，
而 v2 App 的原始名恒为 `tool_call`，所以解析必然返回空，卡片必然被 `Qoe()` 过滤。

**实测**：在工具返回值里补 `details.bridgedTool = { name: "download-file", server: "hana-downloader" }`，
宿主确实把它写进了会话记录（历史投影也读得到），但卡片依旧不出；宿主照样追加
`Card "…" rendered. cardInstanceId: a_…` 那行文案，从工具结果表面看不出任何异常。

**结论**：工具结果的流内卡对 v2 App 在这台宿主上**不可能工作**，不是应用侧能绕的。
可行的出卡通道只剩 `session:send-custom` + `contributes.messageRenderers`，
代价是流式中的投递只能排成 `followUp`，卡片会出现在本回合结束之后。

（另：宿主投影层对 `details.card.cardInstanceId` 是采纳的——给一个符合 `^a_[0-9a-f]{20}$` 的值
就会被原样采用，实测一致。这条可以用来给卡片一个跨重载稳定的身份。）
