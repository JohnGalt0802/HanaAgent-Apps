# hana-downloader-app 踩坑记录

本文件记录 v2 App 迁移过程中踩到并修复的坑。每条按「现象 → 排查 → 根因 → 解法」写，
后三条只写宿主侧通用结论，与下载器本身无关，做其它 v2 App 也会遇到。

宿主版本：HanaAgent 0.946.2（win32-x64）

---

## 1. `/download/*` 是宿主的保留前缀

**现象**：引擎自监听端口后，请求 `/download/status`、`/download/list` 一律 404，
像路径被吃掉了一段。

**排查**：把路径换成 `/wait`、`/list` 这类不带 `/download/` 前缀的写法，立刻正常。

**根因**：宿主的 App 运行时路由把 `download` 当保留段处理，落在 `/download/` 下的
路径在转发前就被截断或改写了。

**解法**：引擎对外暴露的路径避开 `/download/*` 前缀。本项目的实际接口是：

```
GET  /ping
POST /download      ← 这个路径本身没问题，是它下面的子路径有问题
POST /command
POST /wait
GET  /wait
GET  /list
POST /cancel
POST /cancel-all
POST /reveal
GET|POST /settings
GET  /events
```

即：`/download` 作为**端点**可以用，`/download/xxx` 作为**前缀**不行。

## 2. 受管程序的 cwd 不是它的数据目录

**现象**：受管引擎起来后，`tasks.json` 落到了意料之外的位置，或者干脆写不进去。

**排查**：把数据目录打印出来对比，发现 `process.cwd()` 指向 entry 的解析基准目录，
而不是 App 的 `dataDir`。

**根因**：`ctx.runtime.start({ entry })` 里 `entry` 是相对某个基准解析的，
受管进程的 cwd 随之确定，和 App 自己的数据目录没有必然关系。

**解法**：数据目录经 `args` 显式传入，受管程序从 `process.argv` 读：

```js
// app 侧
ctx.runtime.start({ runtime: "node", entry: "engine/server.js", args: [ctx.dataDir] })

// engine 侧
const DATA_DIR = process.argv[2] || process.env.HD_ENGINE_DATA_DIR || process.cwd();
```

不要依赖 cwd，也不要指望它等于 `dataDir`。

## 3. 就绪标记必须独占一行且精确匹配

**现象**：引擎已经监听端口、`/ping` 也能通，但宿主始终认为它没就绪。

**排查**：把就绪输出从 `HD_ENGINE_READY:4317` 改成裸的 `HD_ENGINE_READY`，立刻正常。

**根因**：`service.readyMarker` 是**行级精确匹配**，行里多任何字符（哪怕只是端口号）
都匹配不上。

**解法**：

```js
console.log(READY_MARKER);   // 独占一行，不带任何多余字符
```

注意：本项目后来把 `service` 整个去掉了（见第 4 条），此条对仍在用 service 的
场景有效。

## 4. `runtime.service` 会卡死 app 工具回包（最隐蔽的一条）

**现象**：App 的工具被模型调用后，`execute` 明明在 40ms 内就 return 了，
但模型侧收到的是：

```
App tool "xxx" failed: RPC callback.tools.execute timed out after 30000ms
```

而且工具的**副作用全都成功**（下载照跑、任务照建、结果照投递），只有回包超时。

**排查过程（关键在排除法）**：

1. 先怀疑 execute 太慢 → 日志显示 `returning | +39ms`，**排除**。
2. 再怀疑自己轮询引擎占住了 RPC → 把轮询改成读结果文件（纯 fs，不产生 RPC），
   **仍然超时**，**排除**。
3. 怀疑引擎或 service 长连接 → 写了三个探针工具做对照：

   | 探针 | 行为 | 结果 |
   | --- | --- | --- |
   | `hd_noop` | 什么都不做，直接返回 | **超时** |
   | `hd_log_only` | 只写一条日志 | **超时** |
   | `hd_task_only` | 只做一次 `ctx.tasks.create` | **超时** |

   三个探针日志的时间戳间隔正好 31 秒一个，说明每一个都吃满了 30 秒超时。
   **连"什么都不做"都超时** → 问题与工具内容、与 tasks、与引擎逻辑全都无关。

4. 把 `ctx.runtime.start({ service: {...} })` 整个摘掉再测 → **立刻不超时**。

**根因**：宿主 app-host 侧的工具执行体长这样（`app-host-entry.js` 约 L3461）：

```js
rpc2.handle(AppHostMethod.CallbackToolsExecute, async (params) => {
  // ...
  const result = token ? await runWithAppCallToken(options.pluginId, token, invoke) : await invoke();
  await rpc2.drain();          // ← 等所有挂起的 RPC 排空
  if (result instanceof Response) return http.serializeResponse(result);
  return result;
});
```

而 `drain()` 的实现是：

```js
async drain() {
  while (this.inflight.size > 0) {
    await Promise.allSettled([...this.inflight]);
  }
}
```

`ctx.runtime.start({ service })` 为了让宿主能代理 `/api/apps/<id>/routes/_runtime/<rid>/`，
会保持一条**常驻连接**。这条连接永远在 `inflight` 里，于是 `drain()` 永远转圈，
工具回包卡到 30 秒 RPC 超时。副作用在 `invoke()` 里早就做完了，所以功能看着正常。

**解法**：不用 `runtime.service`，改成**引擎自监听 + app 用 `ctx.network.fetch`**：

```js
// 1. 引擎自己监听回环端口（受管进程内）
server.listen(4317, "127.0.0.1", () => { ... });

// 2. app 侧经受控出网通道访问，清单顶层声明 network
const res = await ctx.network.fetch("http://127.0.0.1:4317/ping", { method: "GET" });
```

```json
"network": {
  "allowedHosts": ["127.0.0.1"],
  "methods": ["GET", "POST"],
  "allowLocalhost": true,
  "defaultTimeoutMs": 30000,
  "maxResponseBytes": 5242880
}
```

注意 `allowLocalhost: true` 必须显式写：缺省为 `false` 时 localhost 与私网地址一律拒绝，
且 HTTP（非 HTTPS）也只在声明了 `allowLocalhost` 后才放行。

前端（iframe 卡片）不能直接敲 4317（CSP + 白名单），另经 App 自己的路由转一手：

```
前端 → /api/apps/<id>/routes/engine/<path> → app 侧 ctx.network.fetch → 127.0.0.1:4317
```

## 5. App 工具的返回值必须是 `{ content: [...] }`

**现象**：不再超时之后，工具回包显示成：

```
(no tool output)
```

**排查**：对比宿主文档里的官方示例，发现返回值形状不同。

**根因**：模型的工具循环期望的返回形状是：

```js
return { content: [{ type: "text", text: "..." }] };
```

返回裸对象（如 `{ ok: true, taskId: "..." }`）宿主认不出，当成"没有输出"。

**解法**：所有工具统一返回该形状；需要给卡片或后续逻辑用的结构化数据放 `details`：

```js
return {
  content: [{ type: "text", text: "已开始下载：xxx\n任务 ID：yyy" }],
  details: {
    card: { route: "/card.html?taskId=yyy", title: "...", aspectRatio: "8:1", cardForm: "flush" },
    download: { taskId: "yyy", state: "pending", ... },
  },
};
```

`details.card` 是**聊天流卡**的触发点：宿主运行时透传，据此在工具块下方挂一个 iframe。

## 6. 聊天流卡的宽度上限 = 卡壳 `clientWidth`，随窗口浮动

> 本文早期版本把这条写成了“宽度由宿主锁定，页面调不动”。那是**错的**，已按实测改写。
> 错误根源见本节末尾“方法论教训”。

**现象**：卡片里三个操作按钮挤成两行，想把卡片改宽。改了卡片上报宽度（`hana.ui.resize({width})`）
与卡片 CSS 的 `max-width`，从 470 调到 540 再到 620，**实测毫无变化**。

**排查**：先查宿主侧。bundle 里的 resize 桥（`resize-bridge` 脚本）只发高度：

```js
if (h !== last) { last = h; window.parent.postMessage({ type: 'hana.card-resize', height: h }, '*'); }
```

确实没有 width 这一维。但《APPS.md》的“尺寸信封”章节给出了权威规则（当前会推送的挂载位表）：

| 挂载位 | height | width |
| --- | --- | --- |
| 聊天流插件卡 | `flexible`，max 为聊天可视区高度上限 | `flexible`，max 为卡壳 `clientWidth` |
| 黑板 / 拆窗帧 | `fixed`，value 为容器 `clientHeight` | `fixed`，value 为容器 `clientWidth` |
| page / widget | `flexible` | `fixed`，value 为容器 `clientWidth` |

即：宽度**不是 locked，而是 flexible**，max 就是卡壳的 `clientWidth`。

**实测验证**：在卡片里直接量四个宽度（真渲染后量 `getBoundingClientRect`）：

```
iw347 dpr1.75 body347 root347 dl347 CW620
```

`body` / `#dl-root` / `.dl` 三者**全部等于 iframe 宽度**，说明容器已完全撑满；
`CARD_WIDTH` 620 够不到，所以从没参与。另一次在更大窗口下测得 `iw937`，
同样四值一致。结论：**卡片宽度 = 宿主 iframe（卡壳）宽度**，随窗口大小浮动。

**根因**（两条同时成立）：

1. 宽度**没有页面→宿主的上报通道**（resize 桥只认 height），页面对"宽于上限"无发言权；
2. 宽度**上限由卡壳 `clientWidth` 决定**，而卡壳宽度跟随宿主窗口/消息区，不是固定值。

**解法**：内容侧向既有宽度贴顶，布局按窄宽设计：

- 首行只放徐章 + 操作按钮（去掉元信息和百分比/大小），让按钮有完整一行可用；
- 按钮组用 `margin-left: auto` 推到最右，把空间用满；
- 百分比/大小与进度条同排（`.dl-row2`）；
- CSS 里把 `html` / `body` / 根容器显式 `width: 100%`，避免块级容器自己缩。

要"比上限更宽"，只能宿主把卡壳做宽，页面做不到。

**方法论教训**：这个坑排查了很久，主要陷在验证手段上。

1. **系统缩放会让截图量像素失真**。这台机器 `devicePixelRatio = 1.75`，截图上的像素
   比 CSS 像素大 1.75 倍。我拿截图目测“卡片约 230px”并据此连改三轮，全部改错方向。
   **先看 dpr，再信截图**。
2. **要数字就让页面自报**。在 DOM 里插一行字、或把值打进转发日志，比用截图目测可靠得多。
3. **测量时机比测量本身重要**。第一版诊断写在 `render` 拼字符串时，那一刻 `.dl` 还没插入
   DOM，量到的是 `0` 和“找不到”；挪到渲染后量才拿到真值。
4. **诊断字色要跟主题**。红字在深色卡上对比度极低，一直看不见，误判为“没生效”。
**说人话**：宿主只给了高度这一扇门，就别再去撞宽度那面墙。

## 7. iframe 里请求 app 自己的路由，必须带表面会话票据

**现象**：聊天流卡前端一直空白，引擎日志里没有任何请求。直接浏览器打开同一路由却正常。

**排查**：`/api/apps/<id>/ui/<file>` 手动请求，返回
`403 {"error":"forbidden","reason":"missing_credential","connectionKind":"local"}`。

**根因**：宿主给 iframe 签了一张表面会话票据，随 iframe URL 的 `appSurfaceSession` 下发；
iframe 内部发起的请求要把这张票据回传到 `X-Hana-App-Surface-Session` 头，
宿主才认它是这张卡发出的。不带就 403。

**解法**：静态页面启动时自读 `location.search` 里的 `appSurfaceSession`，
后续所有 fetch 都带上 `X-Hana-App-Surface-Session` 头。

**另一个同时踩到的**：iframe URL 里宿主还挂了 `hana-theme` / `hana-css`，
主题要自己读参数写 `data-hana-theme` 并挂上宿主样式表，否则卡片在一张白底里突兀地待着。

## 8. 卡片路由不能带 query

**现象**：卡片 `contributes.cards[].route` 写成带 `?taskId=xxx` 的路径，卡要么不渲染要么报错。

**根因**：卡片路由必须是 ui/ 下的**相对静态路径**，不能含 `?` `#` `..` `\`。
查询参数一律不行。

**解法**：route 固定为静态页（如 `/card.html`），需要参数就由页面自己向引擎问，
引擎在无参时回退到“最近一个任务”。本项目里 `/wait` 无 taskId 就回退，
另加 `hdboot` 在拼转发地址前剥掉基址前缀再映射。

## 附：验证方法的教训

这三条不是宿主坑，是排查方法上的坑，但同样值得记：

1. **副作用成功不等于调用成功。** 投递、建任务、下载全都正常，工具回包照样可以超时。
   报错文本里的 "failed" 说的是回包，不是功能。别被它带偏。

2. **对照实验优先于推理。** 这个 bug 单靠读代码推不出来。写一个"什么都不做"的探针，
   比盯着 `drain()` 想半天有效得多。探针要按变量分层：纯返回 / 只写日志 / 只调 tasks，
   一层层排除。

3. **时间戳间隔会说话。** 三个探针每 31 秒执行一个，这个规律直接暴露了"每个都吃满
   30 秒超时"，比逐条看返回值更快锁定真相。
