## 0. 一句话总结

下载完成时，**未收束会话**通过 host `agent/pre-step` 注入 HBR 到下一条 LLM API 请求的 `payload.messages`，agent 在**同回合**感知（真同步）；**已收束会话**走 `deferred:resolve` 异步 triggerTurn 唤醒。

## 1. 三条投递路径

```
下载 settle (done/cancelled/error/stall)
   │
   ▼
delivery.handleFinal(task) / handleStall(task)
   │
   ├─ 静默分支：consumedByWait / canceledBy=agent → 直接 markDelivered + finalizeRegistry
   │
   ├─ tailSettled(jsonl) 判会话状态
   │
   ├─ true (已收束) ────────────────────────────→ deliverAsync
   │                                                  │
   │                                                  └─ bus.request("deferred:resolve")
   │                                                       └─ host deliverCustomMessage
   │                                                            ├─ isStreaming=true → followUp 入队
   │                                                            └─ isStreaming=false → triggerTurn 立即开新 turn
   │
   └─ false (未收束) ────────────────────────────→ enqueueSync
                                                       │
                                                       ├─ pending Map (key=sessionFile::taskId)
                                                       ├─ 30 秒 timer (SYNC_WAIT_MS=30000) + 实时态续等
                                                       │
                          ┌────────────────────────────┴────────────────────────────┐
                          │                                                         │
                  injectForSession 消费 (期内)                     timer 触发 → sessionActive 判断
                          │                                         │                         │
                          ▼                                    active(续等)          inactive(兜底)
                  真同步：HBR 推 payload.messages                  RESCHEDULE             deliverAsync
                  → agent 当前轮 LLM messages 含 HBR              → 等 agent 自然发 API     → followUp/triggerTurn
                  → agent 同回合感知                              → 再注入                 → 异步投递
```

## 2. 真同步注入的 host 机制

### 2.1 host bundle 魔改点（必要前提）

宿主 0.814.0 bundle 不暴露 `sessionHooks` registry，v1 插件契约无法注册 adjudicator。**bundle 必须魔改一行**：

```js
// bundle/index.js:171120
globalThis.__sessionHooks = j;   // 暴露 hooks registry 给插件
```

- **备份**：`<workspace>\_temp\bundle-index.js.0.814.0-魔改前.bak`
- **恢复**：从此备份覆盖回 bundle/index.js 即可
- **运行时配置**：不进 git（每个宿主升级需重新魔改）

### 2.2 plugin index.js onload 注册 adjudicator

```js
// extensions/index.js (lib/index.js bundled)
async function onload() {
  const hooks = globalThis.__sessionHooks;   // 魔改点暴露的 registry
  if (!hooks || typeof hooks.onDecision !== "function") {
    dbgLog(`onload: sessionHooks unavailable`);
    return;
  }
  hooks.onDecision("agent/pre-step", injectVersion, {
    owner: "hana-downloader",
    order: 999,
  });
  dbgLog(`registered agent/pre-step injection adjudicator`);
}
```

`injectVersion` 接收 `{ session, messages }`，调用 `delivery.injectForSession(session.sessionFile, { messages })`，把 pending 中的 HBR 推到 `payload.messages` 并 return 出去。

### 2.3 host decide waterfall 调用链

```
LLM API 请求前 → host decide("agent/pre-step")
   │
   ├─ host 内置 hooks (order 0/10/20) — 媒体处理 / 压缩
   │
   └─ 插件注入版 (order 999) — delivery.injectForSession
         │
         └─ payload.messages.push({ role: "user", content: entry.content, details })
            │
            └─ host spread 到 invocation
                  │
                  └─ agent 下一条 LLM API 请求的 messages 数组里看到 HBR
```

## 5. 三种时机的精确行为

| 阶段 | agent 状态 | isStreaming | injectForSession | timer 触发后路径 | agent 感知时机 |
|---|---|---|---|---|---|
| **A** reasoning 中调工具 | toolUse | true |推 HBR 进 payload.messages | injectForSession 已消费 | **当前轮** LLM API messages 含 HBR ✓ |
| **B** 输出 stop token 中 | stream中 | true | 不调（host 已不调 agent/pre-step）| followUp 入队 | **下一轮** input（被 followUp 消费）|
| **C** stop 已发 + host 处理中 | 处理中 | false | 不调 | triggerTurn 立即开新 turn | **新轮** input |
| **D** pre_reply_interlude | 渲染最终回答 | false | 不调 | triggerTurn | **新轮** input |
| **E** 用户已收到最终回答 | 静默等用户 | false | 不调 | triggerTurn | **新轮** input |

**核心洞察**：
- A 阶段真同步生效（agent 当前轮 API messages 看到 HBR）
- B-E 阶段真同步必然失效（host 不再调 agent/pre-step），但 timer 触发后 host triggerTurn **主动开新 turn**让 agent 看到 HBR（不等用户输入）
- **"等不到"实际不存在**——host triggerTurn 是 host 内部驱动，不依赖用户输入

## 6. buildEntry 双 status 字段设计

```js
function buildEntry(taskId, result) {
  // status（legacyStatus）= success/failed/aborted，宿主 interlude / 前端 detail 兼容
  // event-status（新语义）= done/cancelled/error，agent 应该看这个
  const eventStatus = result.status || (result.state === "done" ? "done" : result.state === "canceled" ? "cancelled" : "error");
  const legacyStatus = eventStatus === "done" ? "success" : eventStatus === "cancelled" ? "aborted" : "failed";
  const action = eventStatus === "done" || eventStatus === "cancelled" ? "none" : "decide";
  const body = JSON.stringify(result, null, 2);
  return {
    customType: "hana-background-result",
    content: `<hana-background-result task-id="${esc(taskId)}" status="${esc(legacyStatus)}" event-status="${esc(eventStatus)}" source="system" plugin="hana-downloader" type="download" action="${esc(action)}">\n${esc(body)}\n</hana-background-result>`,
    display: false,
    details: { schemaVersion: 2, taskId, deliveryId: `sync:${taskId}:${Date.now()}`, eventStatus, action },
  };
}
```

**HBR 根标签完整属性**：task-id / status / event-status / source / plugin / type / action

agent 判断时**优先看 event-status**（done/cancelled/error），status 仅用于兼容宿主/前端展示。

## 7-b. 主动投递（session 实时态判断，2026-09-02）

> 解决「agent 做长任务（搜索/跑脚本）>30s 但实际未卡死，旧固定 SYNC_WAIT_MS 超时误降级」的问题。

### 动机

旧逻辑：unsettled 时 enqueueSync 进 pending，固定等 SYNC_WAIT_MS=30s——超过就 fallback 异步投递。**但 agent 若在做长任务**（如 search 挂起 40s，等工具返回），下载完成时 agent 未发 API，30s 后 pending 被误杀 → 降级异步。而 agent 其实没卡死，工具返回后会发 API（本可同步注入）。

### 机制

**bundle 魔改**（`globalThis.__sessionHooks = j` 旁）暴露 session 实时活跃态：

```js
globalThis.__sessionHooks.isSessionActive = (sessionPath) => {
  try {
    return typeof Z.isSessionStreaming == "function" && Z.isSessionStreaming(sessionPath) === true;
  } catch { return false; }
};
```

`Z.isSessionStreaming(sessionPath)` 比 `_getSessionEntryByPath` 更可靠（公开方法，检查 prePromptAbortControllers + session.isStreaming）。

**投递层 enqueueSync** 超时改实时态判断：

```js
const active = sessionActive(item.sessionPath);
if (active === true && item.waitTotal < SYNC_MAX_WAIT_MS) {  // SYNC_MAX_WAIT_MS=10min
  item.waitTotal += ms;
  logInfo(`[delivery] RESCHEDULE ${key} (${kind}): session active, keep waiting`);
  schedule(ms);  // 续等，agent 自然发 API 时注入
  return;
}
// inactive（收束）→ 立即兜底 deliverAsync 异步投递
```

### 关键设计

| 项 | 值 | 说明 |
|---|---|---|
| `isSessionActive` | bundle 魔改暴露，调 `Z.isSessionStreaming` | agent 是否还在 streaming（跑长任务/工具挂起）|
| active → 续等 | `RESCHEDULE` | 等 agent 自然发 API 注入（agent/pre-step）|
| inactive → 兜底 | `deliverAsync` | 立即异步投递，不等 30s |
| `SYNC_MAX_WAIT_MS=10min` | 续等总上限 | 防悬挂工具永不出结果 |

### 安全回退

`sessionActive` 返回 null（bundle 未魔改 / 路径不对 / 异常）时→ `active === true` 不成立 → 走**原超时兜底**。未魔改 bundle 的环境行为完全回到旧版（30s 超时降级），不受影响。

### 实测验证

```
[06:48:11] RESCHEDULE a3a68b00:stall: session active, keep waiting (30000ms)  ← 长任务续等
[06:48:26] INJECT a3a68b00:stall into next provider request                  ← 15s 后注入
```

旧版 b29d9009 同场景 `[SYNC TIMEOUT]` 误降级 → 新版 `[RESCHEDULE] → [INJECT]` 主动投递成功。

## 10. 已知边界与后续改进

- **bundle 魔改是侵入式**——宿主升级会失效，需重做。理想路径：宿主原生暴露 sessionHooks（dsh 已向宿主团队建议）
- **30 秒覆盖典型场景**——长 reasoning（>30s）走 followUp 兜底，agent 多等一回合但 HBR 不丢
- **HBR 跨多轮保留**——enqueueSync 进 pending 后即使跨多 turn 仍能匹配同一 sessionFile 的 agent/pre-step 调用
- **dlcore fireFinal 已修复**——错误 catch 块移除 fireFinal，统一由 _run() finally 触发（避免双触发覆盖）
- **后续**：宿主 bundle 修复后建议移除 bundle 魔改（dsh 文档 §5.2 双 status 设计建议已在合并中）
