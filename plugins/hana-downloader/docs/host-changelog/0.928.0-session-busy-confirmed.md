# 0.928.0 v2 plugin 真同步投递实测：session_busy 持续 busy（@LOCKED 关键发现）

## 核心结论

**0.928.0 下 hana-downloader v0.12.0 v2 plugin 调用 `bus.request("session:send")` 永远抛 `session_busy` 错**（来自 host bundle L185149）：

```js
if (r.isSessionStreaming(f)) throw new Error("session_busy");
```

**60 次重试 × 500ms = 30s 内** session 始终在 streaming → 重试用完 → fallback `deliverAsync` (deferred:resolve async)。

## 根因分析

1. **session:send 对 v2 plugin caller 走底部分支**（0.928.0 host bundle L185079-185157）
2. 底部分支检查 `isSessionStreaming(sessionPath)` → **agent turn 进行中（思考/工具调用/生成响应）→ true**
3. **agent 永远在 streaming**——工具调用后立即进入下一个 turn（agent 在思考下一步动作）
4. **session:send 永远 busy** → 30s 重试用完 → fallback async

## 关键洞察

**session_busy 不是 bug，而是 host 的合理保护**：
- 防止 plugin 在 agent turn 进行中插入 prompt → 干扰当前 turn 流
- 只有 agent 完全 idle（turn done + 无新 turn）才允许插入

但 agent 在工具调用后**立即进入下一个 turn**（思考下一步）→ session 永远不空闲 → 真同步投递永远走不通。

**这意味着 v0.12.0 v2 真同步投递设计**（sync-attempt → busy retry → fallback）**在持续 agent 活跃场景下根本不可能 work**。

## 修复路线

### 路线 A：去掉 session:send 重试，直接 fallback async（最简）

```js
async function deliverSync(t, result) {
  // 0.928.4 下 session:send 对 v2 plugin caller 永远 session_busy
  // （agent 持续活跃，session 永远不空闲）
  // → 直接走 deferred:resolve async 投递（延迟 30s+）
  await deliverAsync(t, result);
}
```

- ✅ 一行改完
- ✅ 投递延迟从"30s 重试 + async"缩短到"立即 async"（host flush 周期）
- ❌ 仍不是真同步
- 不需要重启 host

### 路线 B：加 idle polling（hack）

```js
// 等 session 空闲（turn done + 无新 turn）再调 session:send
while (await isSessionStreaming()) {
  await sleep(200);
}
// → 但 agent 持续活跃时永远等不到
```

- ❌ 持续 agent 活跃场景永远等不到 idle
- 不可行

### 路线 C：升级 hana-downloader 到 v2 app 形式

- 独立子进程 + `app/process.spawn` capability
- host 行为可能不同（IPC 通道异步通知 agent）
- 但 hana-downloader 作为 community 槽 plugin（不是 apps/ 槽 app），升级路径复杂
- 需要 host 给 v2 plugin 提供新口子
- **当前 0.928.0 没有这种口子**

### 路线 D：等待 host 新口子

- 0.919.4 → 0.928.0 没新增 v2 plugin 真同步口子
- Mc(caller) 永远返回 null
- 等等待 v2 plugin caller 的"verified" 通道

## 推荐：路线 A（去掉重试）

实际行为没区别（agent 都通过 async 收到 HBR），但：
- 节省 30s 等待
- 代码更清晰（不再有伪真同步的承诺）
- 不需要重启 host（plugin 重载即可）
