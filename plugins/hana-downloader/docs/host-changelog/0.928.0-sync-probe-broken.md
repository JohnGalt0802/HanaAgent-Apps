# 0.928.0 sync-probe 实测：设计上不能 spawn（@LOCKED 重要）

## 关键发现

0.928.0 host 内置 `apps/sync-probe/`（"Sync Probe" v1.0.0）作为**官方 v2 app 同步投递探针**——但**设计上不能 spawn 子进程**，apply() 永远不会跑。

## sync-probe vs jimeng-cli manifest 对比

**jimeng-cli**（正常工作的 v2 app）：
```json
{
  "id": "jimeng-cli",
  "capabilities": [
    "app/media.provide",
    "app/process.spawn"   ← 关键：spawn 子进程 capability
  ]
}
```

**sync-probe**（0.928.0 内置）：
```json
{
  "id": "sync-probe",
  "capabilities": ["tools"]   ← 只有 tools，缺 app/process.spawn
}
```

## 0.928.0 host 行为（实测 2026-09-08）

```
L184 [INFO] plugin-loader-v2 builtin app jimeng-cli loaded without a user approval
L185 [WARN] [app-host] [jimeng-cli] (node:27440) PERM0002 ...       ← jimeng-cli 子进程 spawn
L187 [INFO] [media] adapter registered: jimeng-cli-images           ← jimeng-cli apply 跑过
L189 [INFO] plugin-loader-v2 plugin "jimeng-cli" v0.1.0 loaded

L193 [INFO] [ui-contributions] ui contribution "v2-sync-probe" registered
L194 [INFO] plugin-loader-v2 plugin "sync-probe" v1.0.0 loaded   ← sync-probe 标 loaded，但没 spawn
L195 [INFO] [cron] 调度器已启动（间隔 60 秒）                       ← 后续完全没 sync-probe spawn 日志
```

**关键差异**：
- jimeng-cli 有 `app/process.spawn` capability → host spawn node 子进程 → apply() 跑 → 注册 adapters
- sync-probe 只有 `tools` capability → host **不 spawn** → apply() 不跑 → 工具永远不能调

## sync-probe 的实际可用状态

| 项 | 状态 |
|---|---|
| manifest 解析 | ✅ |
| ui-contributions 注册 | ✅（右键消息"sync-test" action）|
| processes.start spawn | ❌（无 app/process.spawn capability）|
| apply(ctx) 执行 | ❌ |
| tools.register("sync_probe_test") | ❌ |
| sync_probe_test 工具可用 | ❌ |
| v2sync.log 生成 | ❌（只有我手动 import 写过）|

**结论**：0.928.0 的 sync-probe 是**设计上有缺陷**——它指向了"右键消息调 sync_probe_test"，但工具永远没注册，UI action 永远点不亮。

## 对 hana-downloader 的影响

hana-downloader v0.12.0 是**v2 plugin**（class 形式，社区槽），不是 v2 app。

| 维度 | hana-downloader v0.12.0（v2 plugin） | sync-probe（v2 app 探针）|
|---|---|---|
| 加载形式 | `export default class { onload() }` | `export function apply(ctx)` |
| 运行方式 | host bundle 内运行（class 实例）| 独立 node 子进程 |
| caller | `{kind:"plugin", pluginId}` | `{kind:"v2app", appId}` |
| Mc(caller) | 返回 null | 返回 pluginId |
| session:send 走底部分支 | ✅（必然）| ❌（走 v2 app 分支）|
| 真同步投递 | ❌（promptSession 可能抛错）| ✅（steer/followUp 真同步）|
| 独立 capability | 不需要 | 需要 `app/process.spawn` |

**0.928.0 没给 v2 plugin 任何新口子**——session:send handler 与 0.919.4 几乎完全相同（仅 Mc() 函数重命名 + 底部分支加 text 校验）。

## 0.928.0 同步投递口子现状（实测确认）

**v2 plugin（社区槽）**：永远走 session:send 底部分支（Mc() 返回 null）→ promptSession → 可能抛错（plugin caller permission 限制）→ 实际只能 fallback deferred:resolve 异步投递。

**v2 app（apps/ 槽）**：需要 `app/process.spawn` capability 才能 spawn 子进程跑 apply() → 才有真同步投递。但 **sync-probe 这个官方探针自己都缺这个 capability**——可能是 0.928.0 的设计/打包遗漏。

## 后续验证方向（受"非必要别反复重启"约束）

1. ~~直接看 sync-probe 实测 session:send 行为~~ → 不可行（sync-probe 没 spawn）
2. **自己写 v2 app 探针 + app/process.spawn capability + 重启 host** → 必须重启 + 测试一次
3. **保持 hana-downloader v0.12.0 现状（async fallback）** → 不重启，已能用

## 给上游建议（如果上报）

sync-probe manifest 应该加 `"capabilities": ["tools", "app/process.spawn"]` 才能正常工作。或者 sync-probe 的 tools 应该通过 contributes.tools 而不是 apply() 注册（让 host 在主进程注册）。
