# 0.938.12 — 桥接方案落地并实测通过：用 v2 app 正门做同步投递

日期：2026-09-09 | 状态：**端到端实测通过**
宿主：0.938.12-win32-x64 | 插件：hana-downloader v0.14.0（投递层改动，版本号未升）

## 0. 方案

下载器要的宽能力（任意 URL / 任意落盘 / spawn）只有 v2 plugin 形态有，而 `agent/pre-step` 正门只有 v2 app 形态有。桥接把两边的长处拼起来：

- **新增 v2 app `hd-sync-bridge`**（`~/.hanako/apps/hd-sync-bridge/`，约 80 行）：只做一件事——注册 `agent/pre-step`，读自己的队列目录，把属于当前会话的回执拼进 messages。
- **插件（v2 plugin，跑在宿主进程内、无沙箱）** 把回执原子写入 `{HANA_HOME}/app-data/hd-sync-bridge/queue/<key>.json`。
- **一条回执只走一条通道**：`ctx.hooks`（app 形态）> 桥接 > 魔改。桥接靠 `ready.json` 心跳判活，心跳过期自动回退魔改通道。

## 1. 改动清单

| 文件 | 改动 |
|---|---|
| `~/.hanako/apps/hd-sync-bridge/manifest.json` | 新增：`capabilities: ["app/hooks.agent-pre-step"]` + icon |
| `~/.hanako/apps/hd-sync-bridge/index.js` | 新增：队列消费 + 注入 + `ready.json` 心跳（30s 节流） |
| `lib/delivery.js` | `bridgeWrite` / `bridgeDrop` / `bridgeConsumed` / `bridgeReady` / `pickChannel`；`enqueueSync` 打 channel 标记；`injectForSession` 只消费 `channel === "hooks"` 的项；桥接项由 30s 定时器按「文件是否被读走」判定，未消费则降级 deferred |
| `index.js` | 计算 `bridgeQueueDir` 并传入投递层，日志打印 `DBG bridge queue dir` |

## 2. 实测证据（2026-09-09 10:32，宿主 0.938.12）

```
10:32:48  下载完成 574,109 B（限速 50KB/s）→ 插件写队列 01d136af-mtthgtq3.json (921 B)
10:32:53  [hd-sync-bridge] INJECT 1 item(s) | session=...01a083ee....jsonl msgs 217->218
          queue 目录清空
          agent 在未收束回合内收到回执，仅一条（无双投）
```

`channel=bridge` 的依据：只有该通道才会写队列文件，且魔改通道的 `injectForSession` 对非 hooks 项直接跳过，所以双投不可能发生（这一点在修 channel 标记前是真实隐患，已消除）。

## 3. 安装与授权（需用户操作，无法代劳）

1. 设置 → Apps → 批准 **下载回执桥**（日志：`plugin "hd-sync-bridge" was started (user)` 10:31:07）
2. 设置 → Security → App capabilities → 打开 `app/hooks.agent-pre-step`（ledger：allowed / always，10:31:07）

## 4. 与魔改的关系

- `restart-hana-reliable.ps1` 仍会在重启前自动补 bundle 魔改，魔改作为**兜底**保留；
- 插件优先走桥接（心跳新鲜时），只有桥接不在线才回退魔改；
- 宿主自动更新不再影响同步投递：桥接 app 在 `~/.hanako/apps/`，是用户数据目录，升级不覆盖。

## 5. 遗留

- 插件版本号仍是 0.14.0，未升（待定）。
