## 1. 结论

桥接方案（`hd-sync-bridge` app + 插件写队列）**继续有效，无需改动**。

插件侧的 `ctx.hooks` 在 0.946.2 依然是 `undefined`，新版本的会话钩子仍是 **App 域专有能力**，没有下放到 v2 plugin。下载器保持 v2 plugin（保留任意 URL / 任意落盘 / spawn 能力），桥接 app 继续持正门注入。

同时确认：9/9 授予桥接 app 的 `app/hooks.agent-pre-step` 权限被新版原样保留，没有要求重新授权。

## 4. 端到端验证

### 同步投递（会话未收束）

下载 2 个小文件，回执经桥接队列注入：

```
[08:59:33.354] [hd-sync-bridge] INJECT 1 item(s) | session=...01a083ee....jsonl msgs 163->164
[09:09:21.824] [hd-sync-bridge] INJECT 1 item(s) | session=...01a083ee....jsonl msgs 175->176
```

队列文件被读走即删除，两条下载的队列都已清空。

### 异步投递（会话已收束）

发起一个 `startDelayMs: 15000` 的下载后主动结束回合，时间线：

```
09:09:27.772  任务 febf26af-mtutxrvj 注册
09:09:40.063  assistant stopReason=stop      ← 会话收束
09:09:47.829  新 turn 自动开始                ← deferred 唤醒
```

间隔 7 秒。下载在 09:09:42 前后完成，此时会话已收束，投递层走 `settled → deferred:register + deferred:resolve`，由宿主 dispatcher 直接开新 turn。

**这是真异步唤醒，不是 30 秒超时降级**（`SYNC_WAIT_MS` 未到期）。

## 5. 其他发现

### task-registry 新 WARN

```
[WARN] [task-registry] no handler for type "download", task <id> registered without abort support
```

0.946.2 新增 task-registry 层，插件注册后台任务时若未提供 handler，宿主拿不到 abort 支持。下载器自己的 `download-cancel` 不受影响，功能未断，属可适配项。

### 与本插件无关但同批开放的 App 能力（备查）

- App 产物交付到指定会话（登记真实资源 / 复制已授权文件）
- 持久后台任务与调度（指定时间 / 按间隔，重启后按授权恢复）
- `runtime.local-machine` 运行模式（需运行 + 本机 + 外网三项授权，以当前系统用户权限访问文件与命令，**不提供隔离**）
- 模型用量与费用查询、模型元数据查询、凭据读取（各自独立授权）
- 跨 App 服务调用、动态快捷键、消息卡映射、斜杠命令别名

## 6. 后续

彻底干净的路线是把 hana-downloader 迁成 v2 App，直接用 `ctx.hooks` 与官方产物交付，删掉桥接和魔改两条兜底。代价是重写投递层、重做权限声明，且 `runtime.local-machine` 在 Windows 上的隔离强度尚未实机验收。**暂不迁移**，等该模式被验证后再议。
