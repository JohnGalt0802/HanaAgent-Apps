# hana-downloader 改造方案：工具发现性 + 代理智能路由

> 起草 2026-09-21，重写 2026-09-24（与「小秘」讨论后修正主轴）
> 状态：**设计稿**
> 一句话：**引擎保留**（它是唯一提供非阻塞执行的机制），**agent 侧感知瘦身**，**工具要更容易被发现**，**代理按目标地址智能路由**。

---

## 〇、上一版方案错在哪（留档）

初稿写的是「从代理下载到观测下载」，主张 agent 裸跑、App 只观察。**主轴是错的**，理由见第一节：

> `exec_command` 是阻塞的工具调用——执行期间 agent 卡住，无法轮询进度、取消、检测卡滞。长程任务没有非阻塞的原生通道。**引擎的价值不是「包装」，而是「非阻塞执行 + 可观测跟进」。**

我把「包装」当成了可去掉的中间层，而它其实是唯一提供非阻塞的机制。**本方案改为：引擎保留，改的是 agent 侧感知与工具发现性。**

---

## 一、为什么必须由 App 托管

两条路的本质差异：

| | 走引擎（托管） | 裸跑（exec_command） |
| --- | --- | --- |
| 执行方式 | 受管进程，后台跑 | **阻塞，agent 卡着等** |
| 长任务期间 | 可轮询、可取消、可测停滞 | **只能硬等** |
| 进度 | 进程内上报，精确 | 旁路推断，粗糙 |
| 失败 / 停滞 | 引擎知道，可直接通知 | 只能猜 |
| 参数自由度 | 受工具参数面限制 | 完全自由 |

**结论**：**想让下载不占住 agent，就必须有人替它托管那个进程。** 所以：

**全部下载流程走 App，不保留裸下载路径。**

---

## 二、当前真正的短板

去掉「要不要包装」这个问题之后，剩下三个真问题：

### 2.1 工具发现性（最重要）

宿主有**精简模式**，工具是**渐进式披露**的。也就是说 agent 在很多情况下**看不到全部工具签名**，**工具描述本身成了它唯一的入口**。

而 LLM 的训练分布里，`curl` / `wget` / `pip install` 是极高频出现的东西。**当描述引导不到位时，agent 会自然地倾向它更熟悉的裸命令**——不是它不听话，是我们的入口没竞争过它的先验。

**这是本方案的第一议题。**

### 2.2 agent 侧感知过重

| 注入点 | 内容 | 是否必要 |
| --- | --- | --- |
| 下载铁律（`agent-pre-step`） | 多行指令 | 必要，但可精简 |
| 4 个工具签名 | `download-file` / `download-wait` / `download-cancel` / `download-command`，各带参数说明 | 部分不必要 |
| 工具返回值 | taskId + 路径 + 进度 + 状态 + 备注 | 大部分不必要 |

「重」的根源在**agent 需要感知的信息量**，不在引擎。

### 2.3 代理行为挡路（已复现的真实事故）

App 主动读取 Windows 注册表的系统代理，于是**国内源也被推去走代理**：

| 场景 | 实测 |
| --- | --- |
| 走代理下 hf-mirror | **0.45 MB/s** |
| curl 直连同一源 | **26 MB/s** |

一旦慢到不可用，agent 就只能绕过工具（那次会话里用户也说「直接先 curl 下吧」）——**绕过之后，卡片、进度、通知、取消全部同时失效**。这是 2.1 与 2.3 叠加出来的最坏结果。

## 三、第一议题：让工具更容易被发现

### 3.1 目标

在**精简模式**下，当 agent 产生「要下载一个东西」的念头时，**我们的工具要在它的候选里胜出**，而不是被 `curl` 的先验压过去。

### 3.2 手段

**① 描述写场景，不写参数**

现在的描述偏「这个工具是什么」，改成「**什么情况下你会需要它**」。模型选工具靠的是场景匹配，不是参数表。

对比：

```
# 现在
任意 URL 文件下载到本地（http/https，支持任意 URL 与任意落盘目录）。

# 改后
要下载一个文件时用这个，而不是 curl / Invoke-WebRequest：
大文件不占住会话、有实时进度、断了能续传、失败会通知你。
```

**② 描述里写明「不用会怎样」**

把代价直接摆在描述里，激活模型的风险判断：

> 裸 curl 会**占住你直到下完**，期间无法回复、无法取消、进度不可见。

**③ 工具名要好认、好想**

`download-file` / `download-command` 已经算直白。可考虑在描述首句重复关键动作词（「下载」「安装」），提高关键词命中概率。

**④ 铁律短而具体**

现在的铁律是多行说明，占上下文且不好执行。改成**一两句 + 可判断的判据**：

> 需要下载 http/https 文件、或安装软件与依赖时，用 `download-file` / `download-command`，不要用 curl / Invoke-WebRequest / pip。
> 判断：预计超过十几秒的下载务必用它（裸跑会占住你）。中途用 `download-wait` 看一次进度即可，不必反复查。

**⑤ 返回值瘦身**

`download-wait` 返回从全量状态压成一行：

```
45%（45MB/100MB），1.2MB/s
```

一行够 agent 判断「硬等还是收束」。文件名、备注、状态文案不必每次都灌。

**⑥ 调用频率降为「关键决策点一次」**

| 现在 | 改后 |
| --- | --- |
| agent 随时可以查 | 关键决策点查一次 |
| 每次返回全量状态 | 每次返回一行进度 |
| 铁律说「按进度决策」（模糊） | 给出具体判据（如「>90% 硬等，停滞则收束」） |

### 3.3 验收方式

用精简模式实跑几个场景（下模型、装依赖、clone 仓库），观察 agent 是否**在无人提示的情况下**选中我们的工具。这是可观测、可复测的指标。

## 四、第二议题：代理智能路由

### 4.1 目标

**国内地址默认直连，国外地址才走代理。** 修掉 2.3 那类事故。

### 4.2 判断策略（两层）

**第一层：域名速判（快，零成本）**

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 国内镜像 / 源 | `*.cn`、`mirrors.*`、`*.aliyun.com`、`*.tuna.tsinghua.edu.cn`、`registry.npmmirror.com`、`hf-mirror.com` | **直连** |
| 国内大厂 CDN | `*.baidu.com`、`*.qq.com`、`*.bytedance.com`、`*.qiniu.com`、`*.myqcloud.com` | **直连** |
| 国外常见源 | `github.com`、`*.githubusercontent.com`、`huggingface.co`、`pypi.org`、`registry.npmjs.org` | **走代理** |
| 未知 | 其它 | **进入第二层** |

**第二层：直连探测（准，有成本）**

对未知域名：**先直连一次轻量请求（HEAD，超时 3 秒）**。

- 通 → 直连
- 不通 / 超时 → 走代理

这一层的好处是**不依赖那份白名单的完备性**，新出现的国内源不会因为没进表而被误推去走代理。

### 4.3 配置出口

延用现有 `config.json`，新增两个键：

```jsonc
{
  "proxy": {
    "mode": "auto",              // auto | always | never
    "url": "http://127.0.0.1:7890",
    "directHosts": ["*.cn", "hf-mirror.com", "..."],   // 强制直连
    "proxyHosts":  ["github.com", "huggingface.co"],    // 强制走代理
    "probeTimeoutMs": 3000
  }
}
```

- `auto`：按 4.2 的两层策略（默认）
- `always`：全走代理
- `never`：全直连（给「我这台机器不需要代理」的场景一个明确出口，这是之前缺的那个开关）

管理器里给一个只读展示 + 三选一的开关即可。

## 五、代理与权限（在别人的电脑上）

这是个真问题：**别人的机器上不一定有代理，也不一定有权限去配。**

### 5.1 定死一条纪律：只读不写

**App 不修改任何系统级设置**，包括：

- 不写系统代理（注册表 `Internet Settings`）
- 不启动 / 不停止代理进程
- 不改防火墙规则
- 不申请管理员权限

理由：那是别人的机器。一个下载工具没有理由去改它的网络配置，而且这类改动**留下的痕迹比它解决的问题更麻烦**。

### 5.2 只做「探测」，按优先级找可用代理

| 顺序 | 探测点 | 说明 |
| --- | --- | --- |
| 1 | 环境变量 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` | 用户或脚本显式设的，优先级最高 |
| 2 | `config.json` 里的 `proxy.url` | 本 App 自己的配置 |
| 3 | 常见本地端口探活 | `7890` / `7897` / `10809` / `1080` / `8080`，**只做 TCP 连通性探测**，不通就跳过 |
| 4 | 系统代理设置 | **只读**注册表，读到就用，读不到就算 |

**注意第 3 条**：探测端口只做「能不能连上」，**不尝试启动任何东西**。

### 5.3 三条降级路径

**情况一：找到代理** → 按第四章的路由策略使用。

**情况二：没有任何代理，但目标需要** →

- **直连试**，失败后**明确告知**：「这个地址需要代理，本机没检测到可用的代理服务」
- 在卡片和返回值里给出**下一步建议**（「如果你有代理，可以在配置里填地址」）
- **不静默失败，也不假装重试**

**情况三：本机没代理，但用户手上有** →

- 提供**一次性配置入口**（管理器里填地址即可），不要求管理员权限
- 若代理本身需要安装（如 Clash 类工具），**App 只提示，不代劳**

### 5.4 一句话原则

> **App 探查环境，不改造环境。**

## 六、agent 侧感知瘦身（汇总）

| 项目 | 现在 | 改后 |
| --- | --- | --- |
| 铁律 | 多行说明 | 一两句 + 具体判据 |
| 工具描述 | 偏「是什么」 | 偏「什么时候用」+ 不用会怎样 |
| `download-wait` 返回 | 全量状态 | 一行进度 |
| `download-wait` 频率 | 随时可查 | 关键决策点一次 |
| 工具数量 | 4 个（含 cancel） | 维持，但描述精简 |

**目标**：在精简模式下，agent 用**最少的常驻上下文**知道「有这个工具、什么时候该用、怎么问进度」。

---

## 七、实施顺序

1. **代理智能路由**（第四章）—— 独立、可立即修，且它是「绕过工具」的直接诱因
2. **代理探测与权限纪律**（第五章）—— 与 1 同批
3. **工具发现性改造**（第三章 ① ② ⑤）—— 描述与返回值重写
4. **铁律改写**（第三章 ④）
5. **调用频率约束**（第三章 ⑥）—— 需要与 `download-wait` 的语义一起调整
6. **验收**：精简模式下实跑场景，看工具是否被自然选中

**版本号**：按普通小版本顺延（不做「V2.0.0」这种大版本叙事）。

---

## 八、对现有能力的影响

**只增不减**：因为不放开裸下载，所有现有能力（卡片、进度、取消、并发队列、限速、回查、通知、管理器）**全部保留**。

新增：代理按地址智能路由、`never` 模式的明确出口、代理探测与降级提示。

移除：无。

---

## 附：一句话版本

**引擎不动，把工具做得让 agent 想得起来，把代理做得别挡路，把别人的机器当成别人的。**
