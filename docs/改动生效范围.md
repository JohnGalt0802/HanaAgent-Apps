# 改动生效范围自查表（hana-downloader-app）

> 每次改完代码、交付之前先过这张表，决定"这次要不要让用户重启"。
> 起因：2026-09-19 的 pnpm 主题分三批交付，用户重启了三次，全是本可避免的。

## 一、对照表

| 改了什么 | 生效方式 | 代价 |
| --- | --- | --- |
| `engine/*`（dlcore、解析器、探测、隧道、server） | **必须重启宿主**。引擎是受管子进程，代码在进程内存里 | 一次重启 |
| `index.js`（工具注册、schema、描述、铁律、结算/查询文案） | **必须重启宿主**。工具 schema 与钩子在 App 进程内注册 | 一次重启 |
| `manifest.json` | 重装 + 重启（变更被宿主当升级处理，reload 不认） | 重装 + 重启 |
| `ui/card.*`、`ui/manager.*`、`ui/shared/*` | 重启后**确定**生效；不重启时新挂载的卡片 / 新打开的管理器通常也能拿到新代码，但宿主会缓存 App 的 iframe 页面（踩坑第 19 条），不确定时按"需要重启"处理 | 视情况 |
| `tests/*` | 不影响运行（离线测试与本地下载源，只有手工跑才执行） | 无 |
| `docs/*`（踩坑记录、规划、README） | 不影响运行，但**必须同步到运行副本**，否则两边漂移 | 无 |
| 配置 / 数据（engine-config、winget settings、任务记录） | 即时生效，运行时读取 | 无 |

## 二、交付前自查（五步）

1. **分类**：这次动过 `engine/*`、`index.js`、`manifest.json` 吗？
2. **归并**：如果还要接着改同一主题的别处，**先改完再交付**。禁止"发现一处、交付一次、让用户重启一次"。
3. **同步**：复制到运行副本 + 全量校验一致。
4. **标注**：报告里区分"已生效（实测通过）"与"待重启生效"，不许含糊成"已生效"。
5. **告知**：需要重启时，明确说清"这次重启换来哪几处生效"，让用户自己定时机。禁止静默重启。

## 三、成色标注约定

- 逻辑层验证（喂真实样本给解析器、抽源码片段跑断言）→ 标"逻辑已验"
- 运行时验证（真跑任务、读卡片 DOM、读实体产物）→ 标"实测通过"
- 只改完代码、没跑过 → 标"待验证"，不许写成"已生效"

## 四、复现过的坑

- 2026-09-19：改完 `engine/*` 不重启，任务照旧走旧解析器（宿主重启前的最后一次实测就是这个状态）。
- 2026-09-24：改 `engine/dlcore.js`（代理解析）后，分别试了 **reload ×2** 与 **install+confirm 重装**，三次都恢复不了 agent 侧工具 —— 报 `RPC peer closed; cannot call callback.tools.execute`。
  两点值得记住：
  - **引擎侧改动确实会因为 reload 而生效**（reload 重启了受管 engine 子进程）：代理解析实测已按新逻辑走直连。断的不是代码，是宿主→App 的**工具回调通道**（`callback.tools.execute`），这条只在宿主启动时建立。
  - 所以“工具调不了就无法验收”是真话：改 engine 后想用工具验证，必须重启宿主；不想重启就只能绕过工具（直接打引擎 HTTP 口 `127.0.0.1:4317`，或让用户自己在界面里操作）。
  - 结论与第一节一致（`engine/*` → 重启宿主），但原因更精确：**不是“代码在内存里”，而是工具回调通道不会在 reload/重装时重建**。
- 2026-09-19：`ui/manager.js` 与 `index.js` 分批改，导致同一功能横跨两次重启。
- 2026-09-17：宿主从 `.hanako\apps\<id>` 副本运行，只改开发目录不生效（踩坑第 21 条）。
