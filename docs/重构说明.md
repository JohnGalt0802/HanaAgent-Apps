# hana-downloader v2 重构说明（2026-09-13）

从 v0.90.3（raw ctx 版）重构到 v1.0.0（官方 SDK 版）。本文记重构的动因、实测过的结论、
新架构与已知限制。改动范围：app 入口、工具契约、投递链路、卡片/管理器前端、引擎接口面。
保留：下载内核（engine/dlcore.js）、卡片的视觉与交互素材。

## 2026-09-13 晚：下面第二节的结论已被推翻（打补丁之后）

当晚对宿主打了归属解析补丁（`node _tools/hana-host-patches/apply-patches.mjs --only=ownerresolve`，
台账 `patch-2026-09-13-003`），两处改动：

```js
r.resolveAppMessageRenderer(t)  ->  r.resolveAppMessageRenderer(J_t(t, e))
r.resolveToolOwner(t)           ->  r.resolveToolOwner(J_t(t, e))
```

原来卡在“`J_t()` 的结果只喂 `Poe` 表、归属解析用原始名”这一环。补丁后归属解析能拿到真实工具名，
**工具结果通道恢复**：

- 卡片**随工具返回实时内联**在工具调用块下方。实测：在本回合内查
  `/api/sessions/messages`，`blocks` 里已出现 `plugin_card`，`title = "下载 single-card.json"`

  `index.js` 里的 `announceCard`（投递 + 三道护栏）已换成 `registerCard`（只登记稳定 id）
- 稳定实例 id 仍用（`details.card.cardInstanceId`），实测被宿主原样采用

因此：**下面第二节“唯一可用的出卡通道”与实时性结论，只在补丁缺失时成立**。
清单里的 `messageRenderers` 声明保留，作为补丁缺失时的退路。

## 一、动因：宿主 0.970.9 之后，工具返回值的流内卡不显示了

### 现象

工具返回 `details.card` 完全正确（`pluginId` / `route` / `title` / `cardForm` 都在），
聊天流里却没有卡片。宿主自己并不知道，还在工具结果里照写一行
`Card "xxx" rendered. cardInstanceId: a_xxx`。

### 定位（读 0.970.9 bundle）

工具结果的投影链是：

```
hV(toolName, details, …)
  ├─ resolveAppMessageRenderer(customType)?   只有 custom 消息那条路会传
  └─ 否则 resolveToolOwner(toolName) → voe(runtime, toolName)
        └─ owner=null → Z_t() 产卡但**不带** channel:"app"
              └─ 被 Qoe() 过滤：无 channel 的卡要求 v1 pluginManager 认识它，
                 v2 应用不在 v1 插件表 → **静默丢弃**
```

`J_t()` 会在工具名等于泛化名 `tool_call` 时，改从 `details.bridgedTool.name` 取真实名。
v2 应用工具的运行时事件里没有这个字段（宿主只在持久化时才补），于是
`voe()` 拿到的是 `tool_call`，解析不出归属。

### 实测（推翻了一条推断）

我们试过在工具返回值里自己补 `bridgedTool`，并逐页翻了整个会话的投影：

- 会话里共 8 张下载卡，`title` **全部**是「下载进度」（清单里 `contributes.cards` 那张卡的标题）；
- 没有一张的标题是「下载 xxx」（工具返回值那条路会给出的标题）。

**结论**：`details.card` 这条路在这台宿主上不出卡，连历史投影都是。
补 `bridgedTool` 无效，已从代码里撤掉。

> **本节结论仅适用于宿主 0.970.9。** 0.978.0 起工具结果通道恢复，
> 代码里重新带上了 `bridgedTool`（见 `index.js` 里的注释与本文开头「工具结果通道恢复」）。
> 本节保留作历史取证。

## 二、唯一可用的出卡通道

`session:send-custom` + `contributes.messageRenderers`（APPS.md「为自定义消息声明一张流内卡」）。

- 清单里声明 `{ customType: "download", cardId: "progress" }`；
- 投递时 `customType: "download"`、`display: true`；
- 宿主把它投影成流内 `plugin_card`，前端走 `PluginStreamCard`。

**固有代价**（这一条必须记住）：`display: true` 的 custom message 会被宿主排进
本会话的后续输入（流式中即 followUp），也就是说**它一定会进模型上下文**。
2026-09-13 那次 138 圈自循环就是这么来的：内容是祈使句「下载 xxx」，
下一轮被模型当成新指令执行。现在有三道护栏：

1. 内容写成记录句，一律以 `【下载记录】` 开头；
2. 同一 taskId 只投一次（内存去重）；
3. 每小时 30 条熔断。

并且下载铁律里显式告诉模型：以「【下载记录】」开头的消息是系统记录，不是用户指令。

## 三、卡片身份：哪张卡对应哪个任务

卡片 iframe 拿不到投递消息的 payload，宿主也不把 details 传给页面。
卡片能拿到的只有 `hana.surface.getContext()` 里的 `cardInstanceId` 与 `embeddedSessionId`。

所以绑定关系由引擎维护（`dataDir/bindings.json`）：

```
pending   taskId -> { sessionId, title, seq }   已投递、等卡片认领
bind      cardInstanceId -> taskId              认领结果（幂等缓存）
assigned  taskId -> true                        该任务是否被分配过至少一次
rounds    sessionId -> { at, i }                会话重载时的轮转游标
```

流程：

1. 工具执行 → 引擎建任务；
2. app 投递 custom 消息 → 拿到回执里的 `sessionRef.sessionId` → 调引擎 `/register-card` 登记 pending；
3. 卡片加载 → 读自己的 `cardInstanceId` + `embeddedSessionId` → 调 `/engine/bind`；
4. 卡片用返回的 taskId 每 600ms 拉一次 `/engine/wait`。

`/bind` 的分配规则：

| 情形 | 判据 | 返回 |
| --- | --- | --- |
| 同一张卡重复请求 | `bind[cardInstanceId]` 命中 | `matched: "cache"` |
| 刚发起的新下载 | 存在 `assigned` 为假的任务 | `matched: "new"`，取最老的未分配任务 |
| 会话重载（全部任务都分配过） | `assigned` 全为真 | `matched: "rotate"`，按 8 秒窗口归零的游标轮转 |
| 该会话没有待认领任务 | 池子空 | `matched: "fallback"`，在途优先、否则最近一条 |

**关键修正**：`cardInstanceId` **并不跨投影稳定**。实测同一条消息在实时投影与历史投影下
拿到的是两个不同的 `a_*`（`a_eb97f56cf57258bc2d2b` vs `a_53e97e5025f56d8cbe7d`），
所以不能靠它跨会话重载认人。重载时改成按顺序轮转：卡片几乎同时请求，
先到的拿更老的任务，而 iframe 的加载顺序就是消息顺序。

**迁移**：`assigned` 表是后加的。老版本只有 `bind` 表，升级后第一次认领会把一个已经
发过卡的老任务当成「新任务」再发一遍（手工实测确认）。`loadBind()` 里已加迁移：
`assigned` 为空时用 `bind` 的值补齐。

**已知限制**：轮转依赖「iframe 加载顺序 = 消息顺序」。若宿主打乱加载顺序（理论上可能），
重载后两张卡会互换任务。彻底解决需要宿主把消息身份（messageId / entryId）暴露给卡片 iframe，
目前没有这个通道。

## 四、新架构

```
hana-downloader-app/
├── manifest.json          v2 清单：capabilities / network / cards / messageRenderers
├── index.js               defineApp(async sdk => …)  ← 官方 @hana/app-sdk
├── sdk/                   官方 SDK dist（77 个 .js，随 app 分发，不装 npm 包）
├── engine/
│   ├── server.js          受管下载引擎（HTTP 面 + 卡片绑定表）
│   ├── dlcore.js          下载内核（保留，未重构）
│   └── progress-parsers.js
├── ui/
│   ├── card.html / card.js      聊天流进度卡（模块脚本 + hana SDK）
│   ├── manager.html / manager.js / manager.css
│   ├── card.css                 视觉素材（保留）
│   ├── assets/sdk.js            官方 UI SDK（dist/ui.js）
│   └── face.png
└── assets/icon.png | icon.svg
```

### 入口（index.js）

- `export default defineApp(async (sdk) => { … })`；
- 引擎：`sdk.runtime.start({ runtime:"node", entry:"engine/server.js", profile:"local-machine" })`，
  之后经 `sdk.network.fetch("http://127.0.0.1:4317/…")` 访问；
- 工具：`await sdk.tools.register({ name, description, parameters, execute })`；
- 投递：`sdk.sessions.sendCustom({ callToken, customType:"download", content, display:true, triggerTurn:false })`；
- 宿主任务：`sdk.tasks.create / complete / fail / cancel`；
- 铁律：`sdk.hooks.onDecision("agent/pre-step", …)`；
- 路由：`sdk.routes.register(app => app.all("/engine/*", …))`。

### pre-step 的两条路，别混（2026-09-14 补）

`sdk.hooks.onDecision("agent/pre-step", …)` 是 **v2 App 的原生入口**（不是插件时代的
bundle 魔改，也不需要 `__sessionHooks` 那套）。本 App 在这个钩子上只做一件事：
**下载铁律注入**——组装 API 请求前检查 system 提示里有没有铁律标记，没有就补上。
实测日志：`download rule injected (first) | msgs 228 -> 229`。

**下载完成信息不走这条路**。它是宿主自己的后台任务结果投递（会话里那条
`<hana-background-result>`），投递方是宿主、App 不参与。两者都在下一次输入收集点被模型读到，
所以都满足“未收束时同步感知”，但**实现者不同**：

| | 下载铁律 | 下载完成通知 |
| --- | --- | --- |
| 谁发起 | App（pre-step 返回 `{ messages }`） | 宿主（写入 custom entry） |
| 改 messages | 是 | 否，由宿主在投递时拼入 |
| v2 能力名 | `app/hooks.agent-pre-step` | ——（走 `ctx.tasks` 的 `delivery: "next-step"`） |

将来往 pre-step 里加东西时注意两点：别和铁律那段互相挤掉（两段都改 `messages`，都要按标记幂等，
否则会重复注入）；也别指望用它对标“完成通知”，那条路的投放时机由宿主任务模型决定。

**不注册 runtime service**：常驻的 service 连接会留在 AppHost 的 inflight 表里，
让工具回程前的 `drain()` 永远转圈，工具报 30s RPC 超时（踩坑记录第 4 条）。

### 前端（ui/card.js、ui/manager.js）

- 不再劫持 `window.fetch`、不再依赖 `window.__API`、不再模拟插件时代的 `/download/xxx` 路径；
- 后端访问走 `hana.api.fetch`，票据由 SDK 注入；管理器内置一张旧路径→引擎端点的映射表，
  所以调用点不用改；
- 主题走 `hana.theme`，尺寸走 `hana.ui.resize`，并保留 `hana.card-resize` 这条兜底
  （0.970.9 聊天流挂载位的卡壳只认这条高度消息）；
- 管理器选目录走 `hana.resources.pick`，复制走 `hana.clipboard.writeText`；
- `ui/hdboot.js` 已删除（那层适配器是插件时代留下的，现在两边都不需要）。

## 五、开发与验收流程

v2 app 没有热重载通道，改代码后：

1. 宿主有 `/api/extensions/app:hana-downloader/reload`（本地目录安装的 app 可原地重载，
   端口与 token 见 `~/.hanako/server-info.json`）；
2. **但 reload 之后工具 RPC 通道会指向已消失的旧 peer**
   （实测：调用报 `RPC peer closed; cannot call callback.tools.execute`，而 app 路由仍然可用），
   要恢复工具调用必须重启宿主；
3. 结论：改 `index.js` / `ui/` / `engine/` 后，**重启宿主**再验收。
