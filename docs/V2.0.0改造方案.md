# hana-downloader V2.0.0 改造方案：从「代理下载」到「观测下载」

> 起草：2026-09-21（John Galt 与大姐讨论整理）
> 状态：**设计稿**，待定优先级后实施
> 一句话：**观测归 App，执行归原生工具；App 的价值从「代你下载」变成「看得见、叫得醒、说得上话」。**

---

## 一、动机

### 1.1 现状

当前 App 把下载行为整个包装了起来，并用软约束要求 agent 走它：

- **工具面**：`download-file`（任意 URL）、`download-command`（git clone / pnpm install / winget install / pip install）、`download-wait`（回查）、`download-cancel`（取消）
- **软约束**：`agent-pre-step` 钩子往上下文里注入「下载铁律」——需要下载 http/https 文件时**必须**使用本 App 的工具，禁止 `exec_command` 里的 curl / Invoke-WebRequest 裸下载

这套设计的初衷是好的：**让每一次下载都有卡片、有进度、有通知、可回查**。但它带来三个真实代价。

### 1.2 三个真实代价

**代价一：强制 + 绕过 = 观测在最需要时丢失（已经发生过）**

某会话实录：App 主动读取 Windows 注册表的系统代理，于是 hf-mirror 的下载被推去走代理，实测 **0.45 MB/s**；而 curl 默认不读注册表，直连实测 **26 MB/s**。agent 只能绕过工具改用 curl（用户当时也说「直接先 curl 下吧」）。**一旦绕过，进度卡、通知、回查、取消全部同时失效。**

结论：当工具的参数面覆盖不了真实场景时，软约束不但没保住观测，反而把观测一起推走了。

**代价二：参数负担**

每次下载都要想清并传递 `url / saveDir / fileName / speedLimit / expectedSha256` 等参数。而走命令行时，这些本来就写在命令里——**包一层等于让 agent 把同一件事说两遍**。

**代价三：认知负担**

agent 每次下载都必须先想起「有这么一个工具」，再想起来它叫什么、参数是什么、返回值怎么看。这违背「工具应当自解释、可被自然调用」的取向。

### 1.3 同类 App 的对照

同一个宿主上的 **DSHana** 只声明了一张卡，且**没有 `contributes.messageRenderers`**——它的聊天流卡片全走工具返回值的 `details.card`。这说明「少声明、走正路」在这个宿主上是可行的形态。本 App 此前两边都声明，卡片中心因此并列两张卡。

## 二、目标形态

```
┌────────────────────────────────────────────────┐
│  Agent 侧                                       │
│  用原生工具下载：curl / wget / git / winget      │
│  参数写在命令行里，自由选择代理、限速、续传        │
├────────────────────────────────────────────────┤
│  App 侧（观测者）                                │
│  ① 钩子看见命令 → 解析目标                       │
│  ② 旁路监控目标大小                              │
│  ③ 前端渲染卡片（走 send-custom + messageRenderers）│
│  ④ 回查 / 通知 / 卡滞叫醒 / 收束建议 / 跨会话管理  │
│  ⑤ 少量只读工具（status / list / verify）        │
└────────────────────────────────────────────────┘
```

**核心分工**：
- **执行归原生工具**：断点续传（`curl -C -`）、限速（`--limit-rate`）、代理（`-x` / `--noproxy`）、重试（`--retry`）、哈希（`Get-FileHash`）——**这些原生都有等价物**
- **观测归 App**：看见、量出、记住、通知、建议

## 三、能力拆分：观测类 vs 控制类

| 类别 | 能力 | 能否独立于「下载走 App」 |
| --- | --- | --- |
| **观测** | 回查进度 | ✅ 本来就是读状态 |
| **观测** | 跨会话列表 / 管理器 | ✅ 纯读 |
| **观测** | 完成 / 失败通知 | ✅ 靠旁路监控 |
| **观测** | 卡滞叫醒、收束建议 | ✅ 靠旁路监控 + `send-custom` |
| **观测** | 哈希校验（`download-verify`） | ✅ 独立工具，给它文件路径和期望摘要即可 |
| **控制** | 断点续传 | ❌ 无法外挂到已运行的进程；用 `curl -C -` |
| **控制** | 限速 | ❌ 用 `--limit-rate` |
| **控制** | 代理选择 | ❌ 用 `-x` / `--noproxy`，**自由度反而更高** |
| **控制** | 并发队列 | ❌ **没有原生等价物**（见 6.3） |
| **控制** | 取消 | ⚠️ 由 agent kill 进程，或 App 按路径匹配进程代杀 |

**一句话**：观测类本来就能独立，控制类几乎都有原生等价物。

## 四、五个已包装行为的可观测性评估

| 已包装行为 | 原生工具 | App 能靠什么观测 | 观测质量 |
| --- | --- | --- | --- |
| **URL 下载** | `curl -o` | 目标文件大小 + HEAD 拿总大小 | **好**（精确百分比、速度、剩余） |
| **winget 安装** | `winget install` | winget 缓存里的下载文件（**这套探测已实现**） | **好** |
| **git clone** | `git clone` | `.git/objects` 目录增长 | **中**（看得见推进，百分比不精确） |
| **pnpm install** | `pnpm install` | `node_modules` 大小 / 包数量 | **粗** |
| **pip install** | `pip install` | site-packages 变化，基本量不出来 | **很差**（只有开始与结束） |

**这张表决定分档策略**：越往下，进度卡的信息量越少。**给 pip 一个进度条，它只会停在 0% 然后突然 100%**，这比没有进度更糟，因为它制造了「在推进」的错觉。

## 五、四条观察链路（实现纲要）

### 5.1 链路总览

```
① Agent 调 curl / git clone / winget ...
        ↓
② 钩子触发（agent-pre-step，调用前即可见命令原文）
        ↓
③ 解析出「这是下载、目标在哪」，登记为一个观察中的任务
        ↓
④ 旁路监控目标大小 → 前端渲染卡片 + 通知
```

### 5.2 各环节现状

| 环节 | 现状 | 需要做的 |
| --- | --- | --- |
| ② 钩子 | **已有** `app/hooks.agent-pre-step`，目前用于注入下载铁律 | **改用途**：不再注入规则，改为识别下载命令 |
| ③ 解析 | 无 | 新增：识别 `curl` / `wget` / `Invoke-WebRequest` / `git clone` / `winget` / `pnpm` / `pip`，并解析出目标路径或 URL |
| ④ 监控 | **部分已有**（winget 的文件旁路探测） | 扩展为通用监控器：文件按大小、目录按量尺（`.git/objects`、`node_modules`） |

### 5.3 解析的边界（要认下来）

命令行写法无法穷尽：`-o` / `-O` / `--output` / `> file` 重定向 / 管道 / 变量拼接 / 脚本封装。

**兜底策略**：解析不出目标的命令，**至少记下命令原文与启动时间**，在管理器里显示为「未知目标」条目，并可被 `download-list` 看到。**认不出来就退化成普通命令**（与不使用本 App 无差别），但不静默丢失。

## 六、通知能力

### 6.1 三条链路

| 能力 | 现状 | 观察式做法 | 改动量 |
| --- | --- | --- | --- |
| **卡滞停止通知** | **纯 App 机制**：引擎落 `stalled/<taskId>.json`，App 每秒扫描后 `send-custom` + `triggerTurn` 叫醒 | 判据换成「目标大小超过阈值不动」 | **判据换、机制不动** |
| **异步通知（收束后唤醒）** | 走 `send-custom` + `triggerTurn`，由宿主决定唤起时机 | **不变**（本就不依赖谁在执行） | **零** |
| **同步通知（在场即时知道）** | 走宿主任务面（`sdk.tasks` + next-step），最准 | 见 6.2 的三档判定 | **判据换** |

### 6.2 完成判定：猜完再确认（三档）

「完成」从「引擎上报」降为「推断」，但可以用一次回查把它重新升级为**确认**：

```
大小稳定 → 先别下结论
        → 第一档：查进程（按 URL / 目标路径匹配 Win32_Process.CommandLine）
             进程还在  → 卡滞，叫醒 agent
             已退出    → 第二档：比大小（对比启动时记录的 Content-Length）
                           相等 → 完成，回执
                           不等 → 失败/中断，回执（带已下载量）
                                → 第三档（可选）：有期望摘要时跑 Get-FileHash
```

**为什么这样够硬**：进程状态直接回答「这事还在进行吗」，不用从文件大小反推。误判窗口只存在于「大小稳定但进程仍在跑」的几秒，而那种情况本来就该走「卡滞」分支，等进程真退出才结算。

**前提**：**宿主没有 post-tool 钩子**。所谓「触发回查」只能由 App 定时轮询（停滞扫描现在就是 1 秒一轮，现成）。**它是定时检查，不是事件驱动。**

### 6.3 并发队列：唯一没有等价物的能力

`maxConcurrent` 是**跨任务的秩序**，只有统一持有下载才能有。放开之后 agent 可能同时开多个 curl 抢带宽。

**补丁（软提示）**：观测到并行下载超过阈值时，投一句建议（「现在有 N 个下载并行，建议排队」）。**不强制，但让 agent 知道**。

## 七、分档落地策略

| 档 | 范围 | 理由 | 代价 |
| --- | --- | --- | --- |
| **档 1** | **URL 下载放开**（agent 直接 curl，App 旁路观测） | 观测最可靠（文件大小），覆盖日常最多的一类下载 | 无（进度精度几乎不变） |
| **档 2** | **git clone / winget 放开** | 有可靠量尺（`.git/objects`、winget 缓存文件） | 进度变粗（git 无精确百分比） |
| **档 3** | **pnpm / pip 保留在工具里** | 放开后观测质量跌得比工具价值还低 | 无（维持现状即可） |

**同时进行的改动**：

1. **去掉「下载铁律」**：钩子不再注入「必须用下载工具」。软约束是强加的，去掉它 agent 才自然。
2. **钩子换用途**：同一个钩子改为识别下载命令、解析目标路径。
3. **只读工具独立**：`download-status` / `download-list` / `download-verify`——**与下载走不走 App 完全无关**。
4. **保留 `download-file`，降级为可选**：agent 想精确控制时仍可用（指定 SHA、限速等）。
5. **保留 `download-command`**：pnpm / pip 继续走它。

## 八、对现有能力的影响

### 8.1 保住的

| 能力 | 说明 |
| --- | --- |
| 进度卡片 | 靠文件旁路监控，**精度接近**（大小 + HEAD） |
| 管理器 | 跨会话列表、筛选、清空，纯读 |
| 回查 | 状态来自观察，与谁执行无关 |
| 完成 / 失败通知 | 三档判定，见 6.2 |
| 卡滞检测与唤醒 | 判据换成「目标大小不动」，逻辑不变 |
| 重试 | App 从钩子记下了原始命令，可以重放 |
| 删除记录 / 文件 | 与执行方无关 |

### 8.2 退化的

| 能力 | 退化程度 |
| --- | --- |
| **进度精度（目录型任务）** | git clone 只能看 `.git/objects` 增长，给不出百分比 |
| **任务身份** | 从「调 API 拿到 taskId」变成「从命令行推断目标路径」。**最脆的一环**；写坏的命令行会认不出来 |
| **取消的精确性** | 从「按 taskId 取消」变成「按路径/进程找」 |
| **SHA 校验的自动性** | 现在内建且不匹配就不交付；放开后要靠 agent 自己记得跑 `Get-FileHash` |

### 8.3 丢失的

| 能力 | 等价物 |
| --- | --- |
| **并发队列（maxConcurrent）** | **无**（见 6.3 的软提示补丁） |
| 统一默认限速 | `--limit-rate`，但每个命令都要写 |
| 代理的统一决策 | `-x` / `--noproxy`，**自由度更高**（现在读注册表反而挡路） |

### 8.4 净判断

**净收益，但要接受两处损失。**

理由：已经发生过「工具参数面覆盖不了场景 → agent 绕过 → 连观测一起丢」的最坏情况。相比之下，「一批下载认不出来」是可控的（退化成普通命令）。**强制 + 绕过是在最需要观测时恰好观测不到**。

## 九、前置依赖与待决项

### 9.1 前置依赖：`messageRenderers` 那一格

钩子是「调用前」触发的，**没有工具返回值**，所以用不了 `details.card`。要让裸下载也能出卡，只剩一条路：

**`session:send-custom` 投递 + manifest 声明 `contributes.messageRenderers`。**

而 `messageRenderers` 会让对应的卡重新出现在卡片中心（宿主对 `contributes.cards` 是**全量列出**，没有「不上架」字段——见《踩坑记录》第 39 条）。

**三选一**：

| 选项 | 结果 |
| --- | --- |
| **A** | 卡片中心保持一张，裸下载**只通知不出卡** |
| **B** | 裸下载也出卡，卡片中心回到两张 |
| **C** | 等宿主给 `cards` 加「不上架」字段，之后两者兼得（已备 issue：`issue-流内卡不该在卡片中心占位.md`） |

**倾向**：**C 或 A**。卡片中心那两个入口的观感，比裸下载的常驻卡片更常被看到。

### 9.2 待实测项

1. `agent-pre-step` 钩子能否稳定拿到**完整命令行原文**（含引号、变量、多行脚本）
2. 按 URL / 路径匹配到正确进程的成功率（同名多任务、短命进程）
3. 目录型量尺的实际开销（递归 `node_modules` 大小的代价）
4. `send-custom` 投递的卡片在**流式中**的表现（已知限制：可能排成 followUp，等本回合结束才出现）
