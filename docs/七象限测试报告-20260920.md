## 一、坐标系

沿用的二维模型：

- **维度 A · 投递时机**：对话**未收束**（unsettled，模型还在跑）/ 已**收束**（settled，模型已停）
- **维度 B · 终态类型**：完成（done）/ 取消（canceled）/ 卡滞（stall）

3 × 2 = 6 个象限，另加象限 7（卡滞 → 恢复 → 完成）。

v2 的语义只有一条：`ctx.tasks` 的 `delivery: "next-step"`（不打断在途请求，下一次输入收集点接收；空闲会话则启动后续回合）。

**两处动作不是由我在回合内执行的**——为造出「已收束」工况，我一旦输出正文就收束了，无法再执行命令。改用独立进程触发：

- **象限 4 的取消**：独立 pwsh 进程在发起后 60 秒 POST `http://127.0.0.1:4317/cancel`，body `{taskId, source:"user"}`。等价于你在卡片上点「取消」，只是触发方不是手指。
- **象限 7 的恢复**：独立 pwsh 进程在发起后 90 秒 POST `http://127.0.0.1:18951/trigger-resume`，模拟网络恢复。

测试期间把引擎的 `maxConcurrent` 临时设为 `0`（不限并发），避免并发队列把任务排进队里干扰观察；跑完已恢复为 `3`。

## 五、卡滞象限（5/6）的行为：与上一轮一致的两段式

1. **卡滞进行中不投递**。引擎只把状态快照写进 `app-data/hana-downloader/stalled/<taskId>.json`，不惊动模型。
   本轮三个卡滞落盘：`91a99410` @ 04:15:40、`2ad2ed1c` @ 04:19:37、`25398744` @ 04:20:07。
2. **转终态时照常投递一次**。断流后任务以 `interrupted` 收终，会话收到一条回执。

根因未变：`ctx.tasks.create` 要投递到会话必须带当前有效的 `callToken`，而它只在工具 `execute` 期间有效。
所以 v2 的投递天然是「一次 execute → 一条终态通知」，中途状态只能靠引擎落盘 + 卡片轮询展示。

象限 5/6 标「行为确认」而非「通过」，与上一份报告口径一致。

## 七、附带发现

1. **新增的三个特性没有破坏投递链路**。限速、并发队列、任务重试都是 2026-09-20 那批改动，
   本轮七个象限全部跑通，宿主任务面与卡片渲染均正常。
2. **`status` 字段的语义是宿主包装的**，不必与引擎终态一一对应：`canceled` 被包成 `status="failed"`、
   正文 `canceled`；`interrupted` 被包成 `status="failed"`、正文带引擎给的错误文案。
   判定终态要看正文与引擎 `/list`，不要只看 `status`。
3. **卡滞的终态来得比源头断流早**。Q5 发起后约 110 秒就 `interrupted`，而 `stall-server` 计划静默 150 秒
   才断流——引擎在卡滞判定（30s）之后另有收尾逻辑，实际提前终止。
4. **引擎设置改完即时生效**：本轮通过 `POST /settings` 把 `maxConcurrent` 设为 0 与恢复为 3，
   两次都是立刻生效，不需要重启。

## 八、补记（2026-09-20 当日，用户复核后）

本报告第三节把象限 5/6/7 标为「行为确认」，口径是「边界符合预期」。**这个口径是错的**。

用户复核时指出：卡滞是「需要 agent 决策」的状态（对端停发，继续等还是取消），
设计意图是**卡滞发生时就叫醒 agent**，而不是憋到终态才通知。现场的三个不对处：

- Q6 的卡滞通知拖到 04:21:13 才到，而卡滞落盘是 04:19:37（中间隔了近两分钟，并且已经晚于 Q7 完成）
- Q7 的卡滞没有任何决策发生：它的 resume 是我在发起时就安排好的外部脚本干的，
  不是「被叫醒后做的决定」
- Q5 虽然投递到了，但也是随终态一起到的，不是卡滞发生时

根因：往会话投递要 `callToken`，而卡滞发生在工具 `execute` 早已结束之后（见第四节），
宿主任务面用不了，所以「中途通知」在当时的实现里根本做不出来。

修法（commit `403d967`）：改用 `session:send-custom` 这条**不依赖 callToken** 的通道
（重试通知已经用过它）。App 侧常驻轮询 `stalled/`，按 `taskId#stalledAt` 去重后
投一条 `download-stall` 隐藏记录，`triggerTurn: true` 直接唤起一轮让 agent 决策；
启动时先静默扫一遍存量，避免重启后回放历史卡滞。
引擎侧 `summarize` 补了 `sessionPath / sessionId / stalledAt` 三个字段。

象限 5/6/7 的正式结论待重测后另出一份报告。
